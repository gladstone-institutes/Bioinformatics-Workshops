SLURM Basics

What is SLURM?

  • SLURM is CoreHPC’s workload manager (job scheduler)
  • It decides what runs where and when across the compute nodes
  • Supports GPUs and interactive jobs natively
  • You describe the resources you need, and SLURM finds a node and runs your job

Key Concepts

  • Login node: where you submit jobs (no heavy compute)
  • Compute nodes: where jobs actually run
  • Partition: a named set of nodes (e.g. cpu, small_gpu)
  • Job: your resource request plus a script; a job step is a command run with srun inside it
  • You rarely SSH to compute nodes, you reach them through SLURM
  • Your jobs run on the half whose login node you connected through, so partition names and paths follow from that

Partitions

Each half groups its nodes into partitions you request by name:

Gladstone

  • cpu : general CPU compute
  • small_gpu : L40s, single-GPU jobs
  • large_gpu : H200, single node
  • pod : multi-GPU H200, by request only

UCSF

  • cpu : general CPU compute
  • gpu : L40s / H100NVL / RTX6000, 1-2 GPUs
  • large_gpu : H200, 4-8 GPUs, condo only for now
  • pod : 8+ GPUs, by request only
  • community : high-throughput, no InfiniBand, 2-week limit

⚠️ Partition names differ between the halves and change as the cluster grows. Always confirm with sinfo on the login node you are using.

A Note on Paths in These Slides

Home and scratch are at the same paths on both halves:

/home/remote/$USER          # 20 GB
/mnt/scratch/user/$USER     # volatile, 30-day purge
/tmp                        # per-job local NVMe, /mnt/lscratch/<job id>
  • Only persistent storage differs: a FAC share (UCSF) or HIVE at /mnt/gladstone/<pi>/<share> (Gladstone)
  • Everything else (SLURM flags, modules, Apptainer) is identical on both halves

Common Commands

Command What it does
sbatch job.sh submit a batch job
salloc ... start an interactive job
srun <cmd> run a command as a tracked job step
squeue -u $USER list your jobs
scancel <jobid> cancel a job
sinfo show partitions and node states
scontrol show job <jobid> full detail on one job
sacct -j <jobid> / seff <jobid> resource usage after a job

Submitting Batch Jobs

Minimal Job Script

#!/bin/bash
#SBATCH --job-name=hello
#SBATCH --partition=cpu
#SBATCH --time=00:05:00
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=1G
#SBATCH --output=hello_%j.out   # %j = job ID
#SBATCH --error=hello_%j.err

srun echo "Hello from $(hostname)"

⚠️ CoreHPC sets no default resources. Set --time, --mem, and --partition explicitly.

Submitting

sbatch hello.sh
squeue -u $USER
[alice@chpc-gs-login-vm1 ~]$ sbatch hello.sh
Submitted batch job 152334
[alice@chpc-gs-login-vm1 ~]$ squeue -u alice
   JOBID PARTITION  NAME  USER ST  TIME NODES NODELIST(REASON)
  152334       cpu hello alice  R  0:03     1 chpc-gs-cpu-01
  • Output lands in hello_152334.out

Resource Requests

CPU and Memory

  • --ntasks : number of tasks (processes); --cpus-per-task : cores per task
  • --mem=16G : total memory per node (or --mem-per-cpu=4G)
  • --time=HH:MM:SS : wall-time limit; --partition=cpu : which nodes
  • ⚠️ --mem is the total for the whole node, not an amount per core

GPU Jobs

Gladstone

#SBATCH --partition=small_gpu
#SBATCH --gres=gpu:nvidia_l40s:1
module load cuda

UCSF

#SBATCH --partition=gpu
#SBATCH --gres=gpu:1
module load cuda
  • --gres=gpu:<model>:<count> requests a specific model; --gres=gpu:1 requests any GPU on the partition
  • ⚠️ Partition names and GPU model strings differ between the halves. Check yours with:
sinfo -o "%P %G"
  • For GPU containers, add --nv to apptainer exec

Pod Partition Note

  • Both halves have an H200 pod on an InfiniBand NDR fabric
    • GPUs share one memory space, so several can work as a single unit
  • Reserved for large multi-GPU jobs; the UCSF half documents a floor of 8 GPUs
  • By request only: a brief consult with an HPC engineer confirms your code can use the architecture
    • On the UCSF half, access is then granted through a SLURM account you specify when submitting
  • Only worth requesting if your code is written for multi-GPU (e.g. DDP), otherwise you are reserving GPUs that sit idle

Job Arrays

When to Use

  • Many similar tasks that differ only by an index (per-sample, per-chromosome)
  • One script, many tasks; SLURM schedules them independently

Example Array Job

#!/bin/bash
#SBATCH --job-name=align
#SBATCH --partition=cpu
#SBATCH --array=1-100
#SBATCH --time=01:00:00
#SBATCH --mem=4G
#SBATCH --cpus-per-task=4
#SBATCH --output=align_%A_%a.out   # %A = array job ID, %a = task ID

srun python process.py sample_${SLURM_ARRAY_TASK_ID}.fastq
  • $SLURM_ARRAY_TASK_ID is 1, 2, … 100 for each task in turn

Interactive Jobs

salloc

Get an interactive shell on a compute node:

salloc --partition=cpu --cpus-per-task=4 --mem=8G --time=01:00:00
  • Use it to prototype, test scripts, or run R / Python interactively
  • CoreHPC has no dedicated dev nodes, so this is how you get an interactive shell
  • For GPU dev work, add your half’s GPU partition and --gres (see the GPU Jobs slide)
  • Browser-based RStudio / Jupyter is also available via Open OnDemand

Attaching to a Running Job

Inspect a job that is already running on a node:

srun --jobid=<JOBID> --pty /bin/bash
# then, e.g. nvidia-smi, top, ls

Monitoring & Canceling

Checking Status

squeue -u $USER             # your jobs and their state
scontrol show job <jobid>   # full detail on one job
sacct -j <jobid>            # accounting after it finishes
seff <jobid>                # efficiency: did you use what you asked for?

Job / Node Status Codes

Job states (squeue)

Code Meaning
PD pending
R running
CG completing
F failed
TO timed out

Node states (sinfo)

Code Meaning
idle free
mix partly used
alloc fully used
drain / maint unavailable
down offline

Canceling

scancel <jobid>     # cancel one job
scancel -u $USER    # cancel all your jobs

Containers in SLURM Jobs

Running Apptainer in a Job

module load apptainer
srun apptainer exec myenv.sif python script.py
  • Build / pull the .sif on the login node first (compute nodes have no internet)

GPU-Enabled Containers

#SBATCH --partition=small_gpu
#SBATCH --gres=gpu:nvidia_l40s:1

module load apptainer cuda
srun apptainer exec --nv myenv.sif python train.py
  • --nv exposes the GPU drivers inside the container
  • Building images: see the container guide

Hybrid Host + Container Workflow

Mix host tools and a container in one job script:

# preprocess with a module-provided tool
module load samtools
samtools sort in.bam -o sorted.bam

# analyze inside the container
srun apptainer exec --bind /mnt/scratch/user/$USER analysis.sif python run.py sorted.bam

MPI / Multi-Node Jobs

MPI Job Script

#!/bin/bash
#SBATCH --job-name=mpi_example
#SBATCH --partition=cpu
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=8        # 16 MPI ranks total
#SBATCH --cpus-per-task=1
#SBATCH --mem=16G
#SBATCH --time=01:00:00
#SBATCH --output=mpi_%j.out

module load openmpi5/5.0.8         # or the MPI bundled with nvidia/nvhpc
srun ./my_mpi_program
  • srun launches one rank per task and wires up MPI across the nodes

Not All Partitions Have InfiniBand

  • MPI needs the fast InfiniBand interconnect, which every partition has except one
  • The UCSF half has a community partition for high-throughput (independent) jobs
    • No InfiniBand, so it is not for tightly-coupled MPI
    • Wall-time limit is 2 weeks, far longer than the other partitions
  • That makes it the right home for long jobs that do not need MPI
  • Academic access is planned for fall 2026, so confirm it exists with sinfo before relying on it.

Pipelines on CoreHPC

Nextflow on CoreHPC

  • Nextflow runs portable, reproducible workflows; nf-core is a community library of pipelines (https://nf-co.re)
  • A driver process submits each pipeline step as its own SLURM job
  • On CoreHPC that driver must be its own SLURM job, not a login-node session
    • The login node kills your processes when the SSH session drops
  • Compute nodes have no internet, so everything is staged in advance
  • Example here: the nf-core/rnaseq pipeline

Nextflow RNA-seq

  • nf-core/rnaseq is the most widely used pipeline

What Makes CoreHPC Different

  • Submit Nextflow itself as a job, which then submits one child job per task
  • Pre-fetch three things on the login node, because compute nodes are offline
    • The pipeline code, its container images, and the plugins it pins
  • Run with NXF_OFFLINE=true so it does not try to phone home
  • Give the driver a long walltime, and always use -resume
  • A few nf-core defaults also need overriding, or -resume breaks

Jupyter / OpenOnDemand

OpenOnDemand Portal

  • A web portal for launching Jupyter, RStudio, and shells in the browser
  • No SSH port-forwarding needed
  • One of the approved ways data leaves CoreHPC, alongside Globus and mounted shares
  • Check the current docs for the portal URL and which apps are published.

Best Practices and Troubleshooting

Best Practices

  • Test interactively in salloc before submitting big batch jobs
  • Request only what you need, and always set --time
  • No heavy compute on the login or bastion nodes
  • Compute nodes have no internet, so stage data and containers first
  • Keep anything you cannot lose on FAC (UCSF) or HIVE (Gladstone), not scratch
  • Staging differs by half
    • UCSF: FAC is not for active compute, so stage data onto scratch first, then copy results back
    • Gladstone: HIVE is mounted directly, so no staging copy is needed
  • For GPU jobs, track utilization with seff / nvidia-smi (low use = wasted reservation)

How Your Jobs Get Prioritized

  • Both halves use fair-share scheduling, not first-come-first-served
    • Higher priority goes to users who have not recently used the cluster
  • UCSF half: no allocation of core hours and no hard usage caps today
    • Labs that bought condo nodes get priority on them, others run there at lower priority
  • Gladstone half: per-user caps on running jobs and GPUs, so check them before planning a big sweep
  • Asking for less runs sooner
    • Oversized requests wait longer, and lower your fair-share standing

Common Errors

  • Job stuck PD (pending): waiting on resources, or the request is too big for the partition
  • OOM / killed: raise --mem or reduce memory use
  • module not found: check the exact name with module avail
  • container cannot see the GPU: add --nv to apptainer exec (and request --gres)

Notes on Using AI on CoreHPC

  • AI assistants (Claude, ChatGPT, Gemini) are great for writing and debugging SLURM scripts
  • But CoreHPC scratch is volatile (30-day purge), so understand any AI-generated script before you run it
  • Double-check resource flags and file paths so a generated job does not delete or overwrite data
  • See the Bioinformatics Core’s guidance on using AI responsibly in research
